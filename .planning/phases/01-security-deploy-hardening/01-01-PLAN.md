<objective>
Give `SecurityConfig` an explicit `CorsConfigurationSource` bean driven entirely by env-overridable configuration, so a future split-origin deploy of `aque-web` is a config change rather than a code change.

Purpose: Closes DEBT-02 / [GH #11](https://github.com/BrininhoBru/aque-backend/issues/11). Today both dev (Angular dev-server proxy) and production (nginx proxying `/api` to `aque-backend:8080`) are same-origin, so nothing needs CORS *right now* — this removes the blocker before the topology changes, without altering current behavior.

Output: A `corsConfigurationSource()` bean, an `app.cors.allowed-origins` property defaulting to empty, and `SecurityConfigTest` proving allow / reject / dev-flow-unchanged.
</objective>

<constraints>
**Deployment topology (read before choosing defaults):**
- Production: the `aque-frontend` nginx container serves the SPA on `https://aque.local` and reverse-proxies `/api/*` to `http://aque-backend:8080/`. The browser only ever talks to nginx — **production is same-origin today**.
- Dev: `aque-web/proxy.conf.json` proxies `/api` to `127.0.0.1:8080` with `changeOrigin: true`. The browser sees one origin — **dev is same-origin too**.
- Consequence: the default value of `app.cors.allowed-origins` MUST be empty. An empty allowlist rejects cross-origin requests (identical to today) while leaving same-origin requests — which carry no `Origin` header — completely untouched. This is what keeps success criterion 5 true.

**Do NOT:**
- Do not call `setAllowCredentials(true)`. Auth is a stateless `Authorization: Bearer` header, not a cookie; enabling credentials would also forbid the `*` header wildcard below and widen the threat surface for no benefit.
- Do not use `setAllowedOriginPatterns` — it accepts wildcard patterns and is exactly the footgun this task exists to avoid. Use `setAllowedOrigins` with an explicit list.
- Do not add a `CorsFilter` bean or a `WebMvcConfigurer#addCorsMappings` override. Spring Security's `http.cors(...)` picks up a `CorsConfigurationSource` bean automatically; a second mechanism would produce duplicate/conflicting headers.
</constraints>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → backend (cross-origin) | An arbitrary third-party web page can issue requests to the API from its own origin; the CORS allowlist decides whether the browser lets that page *read* the response. |
| deploy environment → app config | `CORS_ALLOWED_ORIGINS` is supplied by the operator via the Pi's `.env`; a wrong value here widens the boundary above with no code change. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Spoofing | `SecurityConfig.corsConfigurationSource()` | high | mitigate | Explicit `setAllowedOrigins` allowlist only; `setAllowedOriginPatterns` (wildcard-capable) is banned by an acceptance criterion that greps for its absence. Default value is empty, so an unconfigured environment allows nothing. |
| T-01-02 | Elevation of Privilege | `CORS_ALLOWED_ORIGINS` env var at deploy time | medium | mitigate | `allowCredentials` is left false, so a leaked/overbroad origin still cannot ride the operator's session — the SPA's JWT lives in `localStorage` and must be attached explicitly by script, which the allowlist blocks from reading responses. Plan 02 documents the variable as taking explicit origins only. |
| T-01-03 | Information Disclosure | `SecurityConfig.java` source | medium | mitigate | No production hostname is hardcoded (acceptance criterion greps for the absence of URL literals), so the repo does not disclose the deployment origin. |
| T-01-04 | Denial of Service | preflight handling on `/**` | low | accept | Preflight responses are cheap and unauthenticated by design; the Pi already sits behind a LAN-only mDNS alias. No rate limiting added. |
| T-01-SC | Tampering | npm/pip/cargo installs | n/a | accept | This plan installs **zero** packages — no `pom.xml` change, no package-manager invocation. No Package Legitimacy Audit is required. |
</threat_model>
