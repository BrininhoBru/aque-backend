<objective>
Get the deployed Raspberry Pi off the committed seed credential, and make the rotation a documented, repeatable first-deploy step so a fresh environment cannot silently stay on the seeded hash.

Purpose: Closes SEC-01 / [GH #7](https://github.com/BrininhoBru/aque-backend/issues/7). `V3__seed_user.sql` ships a fixed `admin` username and a bcrypt hash to every environment that runs the migrations; anyone with repo access can attack that hash offline and reach any environment that never rotated.

Output: An automated test proving the rotation mechanism works, a rotation runbook in `fluxo-deploy-aque.md`, and the live Pi actually rotated.
</objective>

<constraints>
**Never edit `src/main/resources/db/migration/V3__seed_user.sql`.** Flyway has already applied it to the production database and recorded its checksum. Editing the file — even to change the hash or add a comment — makes the next boot on the Pi fail migration validation. Rotation happens as a runtime `UPDATE`, never as a migration edit. Adding a *new* `V5__` migration to overwrite the password is equally wrong: it would hardcode a second credential into the repo, which is the exact problem being fixed.

**The agent must never learn the new password.** It is typed by the operator into an interactive prompt during the checkpoint. Nothing in the repo, the plan, the SUMMARY, or any commit message may contain it.

**`../fluxo-deploy-aque.md` is outside this git repository.** It lives in the parent directory `aque/`, which is not a git repo (only `aque-backend/` and `aque-web/` are). Edit the file normally, but do NOT attempt to `git add` it from inside `aque-backend` — that will fail. Record in the SUMMARY that this file was modified but is unversioned.

**Environment facts that constrain the runbook:**
- Postgres runs **natively on the Pi host** (not in a container) — `setup-postgres.sh` created the `aque` database and `aque_user`; the backend container reaches it at `172.18.0.1`. So `psql` is available directly in the operator's SSH session.
- Only the `uuid-ossp` extension is installed (see `V1__create_schema.sql`). **`pgcrypto` is NOT available**, so `crypt()`/`gen_salt()` cannot be used to hash in SQL, and installing it would be an unrequested schema change.
- Docker **is** installed on the Pi (the whole deploy runs on it), so an ephemeral `httpd:alpine` container is the cheapest way to get `htpasswd -B` without installing anything permanently.
</constraints>

    Write `src/test/java/com/aque/auth/AdminCredentialRotationTest.java` in package `com.aque.auth`, `extends BaseIntegrationTest`. Implements SEC-01 (GH #7), de-risking success criterion 1.

    This test exists to retire one specific risk: the runbook in Task 2 tells the operator to generate a hash with `htpasswd -B`, which emits the `$2y$` bcrypt variant, while the application's own `BCryptPasswordEncoder` emits `$2a$`. If Spring rejected `$2y$`, the operator would discover it only after overwriting the password of the sole admin account on a production box with no recovery path. Prove it here, on a real Postgres, before writing the instructions.

    Construct the `$2y$` hash without adding any dependency or shelling out: call `passwordEncoder.encode(<new password>)` to get a valid `$2a$` hash, then replace the first four characters with `$2y$` (`"$2y$" + hash.substring(4)`). The `$2a$` and `$2y$` tags select the identical KDF — only the version marker differs — so this is a faithful stand-in for `htpasswd -B` output. Add a short Portuguese comment on that line explaining that it simulates the external tool's output, so a future reader does not "clean up" what looks like string fiddling.

    Then: build a `User` with username `admin` and that hash, `userRepository.save(...)`, and drive the two behaviors above through the real `authService` (inherited from `BaseIntegrationTest`) — not through a mocked encoder. Use `assertThat(...).isNotBlank()` for the token and `assertThatThrownBy(...).isInstanceOf(...)` for the failure, matching the AssertJ style in `TESTING.md`.

    Name the tests with the three-part Portuguese convention, e.g. `login_hashExternoBcrypt2y_autentica` and `login_senhaAntigaAposRotacao_lancaExcecao`.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public repo → every deployed database | `V3__seed_user.sql` carries a fixed username and bcrypt hash into every environment that runs migrations; repo read access is therefore partial credential knowledge. |
| operator shell → shell history / process list | The new plaintext password crosses this boundary during rotation and can persist in `~/.bash_history` or be visible in `ps` if passed as an argument. |
| operator → agent session | The new password must not cross into the agent's context, the repo, or any commit. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-05 | Information Disclosure | `src/main/resources/db/migration/V3__seed_user.sql` | high | mitigate | Rotate the live credential (Task 3) and make rotation a mandatory documented first-deploy step (Task 2), so any environment reaching production is off the seeded hash. The hash stays in the migration because Flyway checksums forbid editing an applied migration; the seed's value is neutralised by rotation, not by deletion. |
| T-01-06 | Information Disclosure | operator shell during rotation | medium | mitigate | Runbook mandates the interactive `htpasswd -nBC 12 ""` form and explicitly forbids `-b`, keeping the plaintext out of `~/.bash_history` and out of the process list. | T-01-07 | Spoofing | `admin` account, single-user model | high | mitigate | Rotation is verified by a positive *and* a negative login check (new password works, old is rejected), so a silent no-op rotation cannot be mistaken for success. `UPDATE 0` is called out as a stop-and-investigate signal. |
| T-01-08 | Denial of Service | sole admin account | medium | accept | A mis-copied hash locks the only admin out until the `UPDATE` is re-run over SSH. The runbook does pull the official `httpd:alpine` image on the Pi for one ephemeral `--rm` container; accepted as low risk, and its output is self-verifying (a wrong hash simply fails the login check in Task 3). |
